# Patient Domain Architecture

## Scope

Phase 4 strengthens the existing patient module without introducing clinical workflow, fuzzy matching, biometric matching, or full synchronization.

## Patient Model

The PostgreSQL `patients` row contains:

- UUID `patient_id` generated by the backend.
- Unique backend-generated `medical_record_number` using the existing `MRN-<UUID>` format.
- Nullable `no_ktp`.
- Name, date of birth, birthplace, gender, municipality, administrative post, and village.
- `facility_id` with a restrictive foreign key to `facilities`.
- Created and updated timestamps.

Tenant is derived through `patients.facility_id -> facilities.tenant_id`; no client-provided tenant column is trusted for patient ownership.

## API

- `POST /api/pasien/register`: create a patient in the authenticated user's single active facility context.
- `GET /api/pasien?q=...`: list/search up to 50 patients in the authenticated facility memberships.
- `GET /api/pasien/:id`: return a patient only when it is within the authenticated scope.
- `PATCH /api/pasien/:id`: update editable demographic fields within the authenticated scope.

The existing response shape for registration remains `{ success, message, data }`. Detail/list/update responses return the patient domain object.

## Validation

DTOs use the existing `class-validator` foundation. Names and birthplace are trimmed and cannot be blank. Dates must be ISO date strings, gender is restricted to the existing two domain values, and optional demographic fields have bounded lengths. Unknown fields are rejected by the global `ValidationPipe`.

## MRN and KTP Rules

MRNs are generated by the service and never accepted from the client. PostgreSQL enforces MRN uniqueness. KTP is nullable; a partial unique index rejects duplicate non-null values while allowing multiple null values.

## Facility and Tenant Ownership

Patient creation chooses the authenticated user's only active facility membership. A user with ambiguous multiple facility memberships is denied creation until an explicit facility-selection context exists. Patient list, search, detail, and update queries apply membership facility filters. `facility_id`, `tenant_id`, MRN, patient ID, and timestamps are not updateable through the DTO.

## Search and Indexes

Search uses a parameterized TypeORM query over MRN, name, and non-null KTP, with a maximum of 50 rows and facility filtering applied first. Existing indexes cover MRN uniqueness, non-null KTP uniqueness, and facility lookup.

## Clinical History Safety

No delete endpoint was added. Existing clinical visit foreign-key behavior remains `ON DELETE RESTRICT`, so patient administration cannot cascade-delete medical history.

## Flutter Compatibility

The Isar patient model now supports nullable KTP and stores remote MRN/facility metadata. The existing Dio client exposes patient search, detail, and update calls; no new sync engine or authentication UI was introduced.

## Deferred

Soft-delete/archive workflow, national geographic master data, fuzzy identity matching, fingerprint, patient portal, full offline sync, and clinical visit workflow remain deferred.
